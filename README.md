# semis-radar: 반도체 레짐·순환매 레이더

역할 분담
- 데이터 소스(naver/pykrx/KIS) = 사실
- Python = 계산
- 백테스트 = 임계값 검증
- GPT = latest.json 읽고 상태 변화만 알림 (숫자 계산 금지)
- 솬이 = 주도 파트 안에서 눌림 진입 결정

## 판정 규칙 요약

- 추세 ON: 종가 > 20MA, 20MA 5일 상승, 20일 수익률 > 0
- 추세 OFF: 종가 < 20MA 2일 연속, 또는 20MA 하락 + 20일 수익률 < 0
- 신규전환: OFF 10거래일 이상 유지 후 ON 만 인정
- RS 기준: peer 평균 = 그날 유효한 종목들의 20일 수익률 단순 평균. JSON 필드는 `rs20_vs_peers`, `market.peer_avg_ret20_pct`
  - 백테스트 이후 수익률은 별개의 일별 동일가중 누적지수 `ew_index` 기준
- 파트 커버리지: 그날 데이터가 있어야 정상인 종목 대비 유효 종목이 2개 이상이고 66% 이상인 파트만 판정 참여
  - 상장 전이거나 valid_from 이전 종목은 분모에서 빠짐
  - 수신 실패 종목은 분모에 남아서 결측으로 잡힘
  - 제외 파트는 `latest.json.parts_excluded` 에 기록
- valid_from: 해당 날짜 이전 데이터는 지표 계산 전에 잘라서 과거 추세 상태가 넘어오지 않게 함
- 초입후보: 최근 `new_turn_window` 거래일 신규전환 폭 + 참여 파트 수 + 거래량 1.3배 종목 비율
- KOSPI 대비 RS: 참고지표 전용. 어떤 상태 발동/해제 조건에도 사용하지 않음
- 사이클확인: 추세 ON 비율 + 과반 ON 파트 수 + 하닉 추세 ON
- 하닉 본체 주도: 하닉 peer RS 발동 +10%p / 해제 +5%p 미만 **AND 하닉 추세 ON** (v2)
  - 추세 OFF인데 RS만 발동선 이상이면 `hynix_defensive`(상대 방어)로만 기록, 알림 없음
- 주도 파트: 파트 peer RS 중앙값 발동 +8%p / 해제 +4%p 미만, 과반 ON, 과반 거래량 증가
  - v2: 파트 추세 ON 비율이 25% 미만으로 떨어져도 해제 (`part_lead_exit_on_share`)
  - 다른 파트가 진입조건을 만족하면서 현 리더보다 +5%p 이상 강한 상태가 2거래일 연속이면 교체
- 체인: 태그된 고객사 체인별 ON 비율 발동 60% / 해제 40%
- 후반 경고: 후행파트 확산, 주도 RS 고점하락, 대장 신고가 실패, 하닉 추세 OFF, 메모리가격 둔화 중 2개 주의 / 3개 경고 / 4개 이상 강한 경고
  - v2: 사이클확인이 아니면 `해당없음` (평시의 `없음`=경고 해제가 아님)
  - v2: 주도 RS 고점하락은 현재 리더의 최근 20일 RS를 데이터에서 직접 계산. 리더가 바뀌어도 리셋 없음, 리더가 사라지면 사이클확인 구간의 마지막 리더로 평가
  - 메모리가격 입력이 없으면 4항목만으로 같은 임계값 적용 → 사실상 더 빡빡해짐

## 엔진 v2 (2026-11-05)

v1 논리 버그 수정. **단계(phase) 판정은 v1과 동일**하므로 아래 동결 파라미터와 백테스트 v3의 단계 신호 결과는 그대로 유효하다.

| 버그 | v1 증상 | v2 수정 |
|---|---|---|
| 하닉 본체 주도 | 동일가중 소형주 바스켓 대비 RS만 봐서 하락장에서 덜 빠진 하닉이 '주도'로 켜짐. 백테스트에서 평시·사이클확인 켜짐 비율이 19.6%·19.4%로 같음. 2026-11-05 peer -36% 급락 중 추세 OFF 하닉에 '본체 주도 시작' 알림 | 하닉 추세 ON 필수. 추세 OFF면 `hynix_defensive` |
| 주도 파트 유지 | RS만 4%p 넘으면 유지 → 2026-10-16~26 전체 추세 ON 0%인데 '소재' 리더 유지 | 파트 추세 ON 25% 미만이면 해제 |
| 후반 경고 소멸 ① | 사이클확인 이탈 시 항목이 비어 `→ 없음` 알림 (백테스트 14회) | 사이클확인 밖은 `해당없음`, 이 전환은 별도 알림 안 함 |
| 후반 경고 소멸 ② | 리더가 바뀌면 RS 기록이 리셋돼 5일간 RS 고점하락·신고가 실패 계산 불가 → 2026-10-15 '주의 → 없음' 다음 날 평시로 붕괴 | 리더 RS를 데이터에서 직접 계산, 리더 상실 시 마지막 리더 유지 |
| OOS 채점 방향 | '사이클확인→평시', '후반 경고 상승' 같은 하락 쪽 알림도 매수 품질 기준으로 채점 → 경고가 맞으면 실패로 셈 | 이벤트별 방향 채점 (`oos_evaluation_policy_v2.json`) |
| 운영 | freshness guard가 오늘 생성+정상만 봐서 소스가 늦게 갱신되면 그날 판정 누락 / history.csv 를 두 스크립트가 다른 열 구성으로 씀 | guard에 asof==오늘 조건 / history는 oos_tracker 단독 |

v2 전환 첫 실행은 `[엔진 v2 전환] 기준선 재설정` 알림 1회만 보내고 v1 상태와 비교하지 않는다.

**머지 전 확인할 것:** 후반 경고는 v1에서 리셋 버그 때문에 RS 고점하락 항목이 거의 계산되지 않았다. v2에서는 매일 계산되므로 경고 빈도가 늘 수 있다. `semis-radar-backtest` 워크플로를 이 브랜치에서 돌려 `단계별·후반경고별 이후 바스켓 수익률`에서 경고가 셀수록 이후 수익률이 낮아지는지, 빈도가 감당 가능한지 먼저 본다.

## 운영 파라미터 동결 (2026-10-06)

2015~2026 네이버 수정주가 일봉으로 자동 사이클, 랜덤 기준선, 진입 품질, 그리드, 하나 빼고 검증(LOCO)을 거친 뒤 아래 값을 운영값으로 동결한다.

- `new_turn_window = 10`
- `early_enter_breadth = 0.25`
- `confirm_enter_on_share = 0.60`
- `confirm_min_parts = 5`
- `confirm_exit_on_share = 0.45`

근거:
- 35%/5일/60%/5파트: 신호 47개, 헛방 5개, 자동사이클 첫 진입성공 3개, 품질통과율 50.0%
- 25%/10일/60%/5파트: 신호 61개, 헛방 9개, 자동사이클 첫 진입성공 4개, 품질통과율 44.8%
- LOCO 5개 중 4개 fold가 25%/10일/60%/5파트를 선택
- A1을 제외한 fold만 더 엄격한 값을 고른 것은 느린 초기 사이클 A1까지 잡을지의 민감도 트레이드오프로 해석

이 값은 신규 표본 밖 데이터가 충분히 쌓이기 전까지 결과를 보고 재튜닝하지 않는다.

## 백테스트 v3

평가를 세 층으로 나눈다: 사이클 탐지 / 진입 품질 / 랜덤 기준선.

- **자동 사이클(메인)**: 동일가중 지수 지그재그 25% 전환, 저점→고점 +50% 이상, 120거래일 이상
- **수동 사이클**: 과거 비교용일 뿐 정답지로 사용하지 않음
- **진입 품질(고정, 튜닝 금지)**: 신호 후 60거래일 MAE가 -10% 이내 AND 120거래일 수익률이 전체 판정 가능일의 120일 수익률 중앙값 이상
- **신호 라벨**: 헛방 / 너무 이름 / 선행 진입 성공 / 진입 성공 / 진입 실패 / 후반 재진입 / 판정대기(기간부족)
- **랜덤 비교**: 같은 개수의 랜덤 날짜를 5000회 뽑아 사이클 안 비율과 120일 평균 수익률 백분위를 비교
- **LOCO**: 사이클 하나를 빼고 나머지로 파라미터를 고른 뒤 빠진 사이클로 테스트

2026-10-06 실데이터 기준 자동 사이클은 5개:
- A1 2015-08-24 → 2017-11-24
- A2 2019-01-04 → 2020-02-17
- A3 2020-03-19 → 2021-12-30
- A4 2022-09-30 → 2024-06-19
- A5 2024-12-09 → 2026-06-12

추가 진단: 각 사이클 시작 -60 ~ +120거래일의 모든 판정 가능 날짜를 진입 후보로 놓았을 때 고정 품질기준 통과율은 A1 31.5%, A2 14.4%, A3 50.3%, A4 53.0%, A5 45.3%. A2는 구조적으로 좋은 진입점이 드문 사이클이고, A1은 통과 가능한 날이 약 1/3이라 사이클 모양과 당시 얇은 유니버스/신호 선택 문제가 함께 섞였을 가능성을 열어둔다. 레짐 탐지 신호를 곧바로 매수 신호와 동일시하지 않는다.

## 실전 표본 밖(OOS) 평가 v2 (현행)

`oos_evaluation_policy_v2.json`이 유일한 기준. 시작일 2026-11-06, 엔진 v2가 만든 이벤트만 채점한다.

- `latest.json.alert.events`의 이벤트마다 `output/oos_events.csv` 에 한 줄
- `basket_bull` (단계 상승): MAE60 >= -10% AND fwd120 >= 13.97% 이면 통과
- `basket_bear` (단계 하락, 후반 경고 상승): **60거래일 뒤 바스켓이 실제로 내려가 있으면(fwd60 <= 0)** 통과
  - 초안의 '매수 품질 불통과 = 적중'은 오르기만 덜 올라도 적중으로 세서 폐기
- 적중률은 50%가 아니라 백테스트 `event_validation._base_rates`(아무 날에 같은 규칙 적용)와 비교
- 후반 경고는 매도 신호가 아니라 참고 지표
- `rel_outperform` (하닉 주도·주도 파트 시작): 주체 60거래일 수익률 > 바스켓이면 통과
- `rel_underperform` (주도 해제): 주체 60거래일 수익률 < 바스켓이면 통과
- 체인, 후반 경고 하락, 데이터, 엔진 전환 이벤트는 기록만
- 재튜닝 게이트: 새 자동 사이클 1개 확정 OR 채점 이벤트 10개 이상(방향별 최소 3개)

## (폐기) 실전 표본 밖(OOS) 평가 V1

아래는 기록용. V1 대기 행은 `history.csv`에 `v1_retired`로 남고 채점하지 않는다.
`oos_evaluation_policy.json`을 유일한 사전등록 기준으로 사용했다. 동결일은 2026-10-06, 실제 OOS 시작일은 2026-10-07이었다.

- 모든 시장상태 알림은 `output/history.csv`에 날짜·종류·원문을 누적
- 알림 종류: `phase_change`, `leader_change`, `late_change`, `chain_change`, `data_recovery`, `data_error`
- 성과 채점 대상은 **단계 전환 / 주도 변화 / 후반 경고**만. 체인·데이터 알림은 기록만 하고 성과 채점 제외
- `phase_change`의 단순 재진입은 매수 신호가 아니라 **아직 사이클이 살아 있다는 참고**로 해석
- 각 성과 채점 대상 알림은 120거래일이 지나면 `oos_tracker.py`가 자동 채점
- 고정 품질기준: **60거래일 MAE >= -10.0% AND 120거래일 수익률 >= +13.97%**
  - +13.97%는 2026-10-06 전체 판정 가능일의 120거래일 수익률 중앙값(표시값 14.0%)이며 OOS 평가 중 이동시키지 않음
- 채점 기준 바꾸기 금지
- 재튜닝 허용은 아래 둘 중 하나를 처음 충족했을 때만:
  1. 동결일 이후 시작한 새 자동 사이클 1개가 기존 자동사이클 규칙으로 완전히 종료·확정
  2. 신규 성과 채점 대상 알림 10개 이상이 각각 120거래일 성숙 후 채점 완료
- 위 조건 전에는 숫자가 거슬려도 **NO_RETUNE**

## 알림 규칙

- 비교 기준은 `latest.json.last_ok_state` = 마지막 정상 판정 상태. 실행이 하루 빠져도 그 사이 변화를 놓치지 않음
- 첫 정상 실행: 기준선만 만들고 알림 없음
- 새 일봉 없음(휴장일·재실행): 알림 없음
- 데이터 오류: 직전 오류와 내용이 달라졌을 때만 재알림
- 오류 → 정상 복귀: `[데이터 정상화]` 1회
- 하닉·삼전 첫 일봉이 요청 시작일보다 20일 이상 늦으면 소스 기간 잘림으로 보고 판정 보류
- **장중 오염 방지:** 평일 15:40 KST 전 `naver/pykrx/KIS` 실행은 판정·파일 저장 자체를 스킵한다.
  - `late_close_dates`에 지정된 날은 16:40 이전 실행 차단
  - 정말 장중 진단이 필요할 때만 `--allow-intraday` 사용
  - 생산 스케줄에서는 `--allow-intraday` 금지

    1. generated_at 날짜가 오늘이 아니면 "레이더 파이프라인 멈춤: 마지막 실행 (generated_at)" 알림.
    2. data_ok 가 false 이고 alert.changed 가 true 면 alert.message 를 그대로 알림.
    3. alert.changed 가 true 면 alert.message 를 그대로 전달하고,
       state.phase_kr, state.leader, state.active_chains, state.late_level,
       market.breadth_early, market.on_share 값을 JSON에 적힌 숫자 그대로 덧붙여라.
    4. alert.changed 가 false 면 아무것도 보내지 마라.
    5. 숫자를 직접 계산하거나 추정하지 마라. JSON에 없는 값은 "없음"이라고 써라.
    6. state.late_level 이 "해당없음"이면 사이클확인 단계가 아니라는 뜻이다. 경고 해제로 표현하지 마라.
    7. state.hynix_defensive 가 true 면 "하닉 상대 방어(주도 아님)"라고 한 줄 덧붙여라.

## 고객사 태그

`universe.json` 각 종목 `chain` 을 사업보고서/IR의 주요 매출처 근거로 `하닉 / 삼전 / 공통 / 기타AI` 중 하나로 수정.
`미확인`은 체인 집계에서 제외한다. 기억으로 추정하지 않는다.

## 상장일(list_date) / valid_from 가드

- 모든 종목은 기본적으로 요청 시작일부터 데이터가 있어야 정상
- 진짜 늦게 상장한 종목만 `universe.json`에 KRX 상장일을 `list_date`로 기입
- 첫 일봉이 기대 시작일보다 20일 넘게 늦으면 백테스트 중단
- `첫 수신일 != 회사 상장일`이 항상 데이터 잘림을 뜻하지는 않음
- SPAC 합병, 인적분할, 흡수합병 등으로 같은 티커에 다른 사업체의 과거 가격이 붙는 경우는 `valid_from`으로 현재 사업체 기준 시작점을 명시
- 현재 이 규칙을 피에스케이홀딩스와 와이씨에 적용

## 늦은 마감일

- 수능일처럼 정규장 마감이 16:30으로 늦는 날은 `params.json.late_close_dates`에 기입
- 2027학년도 수능: **2026-11-19**
- 생산 실행은 16:50 KST라 늦은 마감일에도 20분 여유를 둠

## 데이터 소스 교체

`data_provider.py`에 provider 클래스 추가 → `get_provider()` 등록 → `daily.yml`의 `--provider` 값만 변경.
계산 코드는 건드리지 않는다. API 키는 GitHub Secrets로만 주입한다.

## 한계

- Naver fchart는 비공식 엔드포인트다. 현재 GitHub runner에서 실데이터 수신을 검증했지만 구조 변경 시 깨질 수 있음
- Naver XML은 EUC-KR이므로 명시적으로 디코딩 후 파싱함
- 거래대금 대신 거래량 배수를 사용
- KOSPI 수신 실패는 참고지표만 사라질 뿐 레짐 판정에는 영향 없음
- 백테스트는 현재 살아남은 종목 중심이라 생존편향이 있음
- 자동 사이클도 5개뿐이라 통계 표본은 작음
- 동결값 25%/10일의 랜덤 대비 120일 평균수익률 백분위는 **57.2**, 사이클 내부 비율 백분위는 **66.8**로 엣지는 약하다. 재진입 하나하나를 매수 신호로 쓰지 않는다.
- 이 시스템의 핵심 실전 용도는 **단계 전환, 주도 파트/하이닉 주도 변화, 후반 경고**다. 실제 진입은 주도 파트 안에서 눌림 여부를 별도로 판단한다.
